# 图片处理流水线 SDK 使用指南

> 适用对象：要集成 `imgpipe` 的业务方。
> 当前状态：阶段 1（同步内核）与阶段 2（异步执行）已实现；取消与生命周期为阶段 3。
> 未实现的能力在文中明确标注。

## 1. 这个 SDK 能帮你做什么

一句话：**你告诉它「有哪些步骤、谁依赖谁、进度怎么通知」，它负责按顺序、按并发执行，并在每一步的状态变化时回调你。**

它解决的是「流程编排」问题：

- 步骤有严格先后（解码必须早于缩放，编码必须早于保存）
- 有些步骤可以并行（A 之后 B、C 可同时跑，最后汇到 D）
- 业务方要感知进度（进度条、日志、埋点）
- 用户可能中途点「取消」
- 某一步失败，后续步骤要自动跳过并通知

## 2. 它不做什么

- **不做图片处理本身**：不解码、不缩放、不加滤镜。这些算法仍由你的业务函数实现。
- **不替你写业务逻辑**：不要把「下一步做什么」写进回调里，回调只用来**观察**状态。
- 不管理你的内存/文件/网络；步骤函数里要做什么由你决定。

可以把它理解成「带进度通知和取消能力的 DAG 执行器」。

## 3. 核心概念

| 概念 | 说明 |
| --- | --- |
| `Step` | 一个可执行动作，用 `std::function<void()>` 表示 |
| `StepId` | 添加步骤时返回的句柄，用于建立依赖和识别回调 |
| 依赖（DAG） | `AddDependency(downstream, upstream)` 表示 upstream 完成后才能跑 downstream |
| `Listener` | 状态变化回调 `(StepId, StepState, const Error&)` |
| `Config` | 执行配置，目前只有 `maxConcurrency`（线程池大小） |

### 步骤状态（StepState）

```
Pending ──▶ Running ──▶ Succeeded
                    ├─▶ Failed
                    ├─▶ Skipped     （上游失败/取消）
                    └─▶ Cancelled   （被显式取消，阶段 3）
```

## 4. 快速上手（异步）

```cpp
#include "image_pipeline.h"

#include <fstream>
#include <stdexcept>
#include <vector>

int main() {
    using namespace imgpipe;

    // 1) 创建流水线（唯一入口）
    Config cfg;
    cfg.maxConcurrency = 2;
    auto pipeline = Pipeline::Create(cfg);

    // 2) 声明步骤：只登记，不执行
    std::vector<unsigned char> raw;

    StepId load = pipeline->AddStep("load", [&] {
        std::ifstream in("input.jpg", std::ios::binary);
        if (!in) throw std::runtime_error("open failed");
        raw.assign(std::istreambuf_iterator<char>(in), {});
    });

    StepId decode = pipeline->AddStep("decode", [&] {
        if (raw.empty()) throw std::runtime_error("decode failed");
        // 你的解码实现
    });

    StepId resize = pipeline->AddStep("resize", [] { /* 缩放 */ });
    StepId watermark = pipeline->AddStep("watermark", [] { /* 水印 */ });
    StepId encode = pipeline->AddStep("encode", [] { /* 编码 */ });
    StepId save = pipeline->AddStep("save", [] { /* 落盘 */ });

    // 3) 建立依赖：参数顺序是 (下游, 上游)
    pipeline->AddDependency(decode, load);
    pipeline->AddDependency(resize, decode);
    pipeline->AddDependency(watermark, resize);
    pipeline->AddDependency(encode, watermark);
    pipeline->AddDependency(save, encode);

    // 4) 注册通知：RunAsync 下回调在库内 worker 线程触发，注意线程安全
    pipeline->SetListener([](StepId id, StepState state, const Error& err) {
        if (!err.ok()) {
            // 记录失败信息
        }
        // 只做观察：更新进度条、打日志、埋点
    });

    // 5) 异步执行：立即返回，回调稍后到达
    if (!pipeline->RunAsync()) {
        // 重复执行或存在环
        return 1;
    }

    // 6) 需要时阻塞到收敛
    pipeline->Wait();
    return 0;
}
```

### 同步用法

如果希望调用线程直接跑完整张图（例如命令行工具、测试）：

```cpp
pipeline->Run();   // 阻塞；步骤和回调都在当前线程
```

### 同步与异步怎么选

| | `Run()` | `RunAsync()` + `Wait()` |
| --- | --- | --- |
| 步骤执行线程 | 调用线程 | 线程池 worker |
| 回调线程 | 调用线程 | worker |
| 是否阻塞 | 是 | `RunAsync` 否，`Wait` 阻塞 |
| 适合场景 | 命令行、单线程工具、测试 | GUI、服务端、需要保持响应 |

> GUI 程序不要在主线程调 `Run()`；用 `RunAsync()`，并把回调转回 GUI 线程。

### 菱形依赖（并行）

```cpp
StepId a = pipeline->AddStep("A", ...);
StepId b = pipeline->AddStep("B", ...);
StepId c = pipeline->AddStep("C", ...);
StepId d = pipeline->AddStep("D", ...);

pipeline->AddDependency(b, a);
pipeline->AddDependency(c, a);
pipeline->AddDependency(d, b);
pipeline->AddDependency(d, c);
```

B、C 在 A 完成后可并行（受 `maxConcurrency` 限制），D 等 B、C 都成功后才开始。

## 5. 线程模型

- `Run()`：所有步骤与通知都在**调用线程**，不涉及线程池。
- `RunAsync()`：步骤与通知都在**内部线程池**的 worker 上；池大小 = `maxConcurrency`（默认 2）。
  - 不同 Step 的回调可能并发 → 业务回调必须线程安全
  - 同一 Step 的通知串行：`Pending → Running → 终态`
  - 上游 `Succeeded` 一定先于下游 `Running`
- `Wait()`：在调用线程阻塞，直到本轮所有步骤到达终态。

## 6. 接口说明

| 接口 | 语义 |
| --- | --- |
| `Pipeline::Create(const Config&)` | 静态工厂，返回接口指针；业务方不直接 new |
| `AddStep(name, fn)` | 构图阶段调用，返回 `StepId`；执行开始后禁止调用 |
| `AddDependency(downstream, upstream)` | 构图阶段调用；上下游必须已存在，不允许自环；执行开始后禁止调用 |
| `SetListener(listener)` | 注册/注销通知；运行中注销的线程安全为阶段 3 |
| `Run()` | 同步执行，在调用线程阻塞到全部步骤收敛 |
| `RunAsync()` | 异步执行，投递根节点后立即返回；重复/并发调用返回 `false` |
| `Cancel()` | 目标语义：Running 的步骤允许完成，未开始的转 `Cancelled`（阶段 3 实现） |
| `Wait()` | 阻塞到当前执行（`Run` 或 `RunAsync`）收敛；无执行时立即返回 |

> `AddStep`/`AddDependency` 在执行开始后调用会抛 `std::logic_error`；
> 非法的依赖（未知 id、自环）会抛 `std::invalid_argument`。

### 回调契约（必须遵守）

1. 回调线程取决于入口：`Run()` 在调用线程，`RunAsync()` 在库内 worker 线程；**业务需自行保证线程安全**。
2. 同一个 `StepId` 的通知串行，顺序是 `Pending → Running → (Succeeded|Failed|Skipped|Cancelled)`。
3. 上游的 `Succeeded` 通知一定早于下游的 `Running` 通知。
4. 回调应短小非阻塞；回调内**可以**调用 `Cancel()`，**不允许**调用 `AddStep`/`AddDependency`。
5. 回调抛出的异常会被库捕获、不会穿透到 worker 线程（当前实现为吞掉；是否转 `Failed` 留待阶段 3 决策）。

### 错误与取消

- 步骤失败：在步骤函数里抛异常。库捕获后该步转 `Failed`（`Error.code = 1`），所有下游转 `Skipped`。
- 有环：`RunAsync()` 启动前做静态检测，环上节点收到 `Pending → Failed`（`Error.code = 2`），`RunAsync` 返回 `false`。
- `Cancel()`：**阶段 3**，当前是空实现。
- 正在执行中的 `Cancel` / 运行中 `SetListener(nullptr)` / 运行中析构，均属阶段 3 内容。

## 7. 集成姿势

推荐：

```cpp
// 回调只负责观察；异步模式下回调在 worker 线程
pipeline->SetListener([&ui](StepId id, StepState st, const Error& e) {
    // Qt：通过 queued signal / QMetaObject::invokeMethod 转回 GUI 线程
    ui.update(id, st, e);
});
pipeline->RunAsync();
```

不推荐：

```cpp
// 不要在回调里写下一步逻辑，编排应该由依赖关系表达
pipeline->SetListener([&](StepId, StepState st, const Error&) {
    if (st == StepState::Succeeded) { /* 手动触发下一步 */ }
});
```

## 8. 构建接入

```cmake
# 仓库根目录已 add_subdirectory(src)，src 下已注册 20-sdk
target_link_libraries(your_app PRIVATE 20-01-picture)
# 头文件路径由 PUBLIC include 自动传播，直接：
#include "image_pipeline.h"
```

- 库产物：`build/lib/20-01-picture.lib`（MSVC）或 `.a`（MinGW）
- 语言标准：C++17
- 线程池：Boost.Asio `boost::asio::thread_pool`（通过 vcpkg 提供，header-only，`PRIVATE` 依赖）
- 配置：`maxConcurrency` 默认 2，线程池在首次 `RunAsync()` 时创建

## 10. 常见问题

**Q：能不能在回调里改图 / 加步骤？**
不能。执行开始后 `AddStep`/`AddDependency` 会抛 `std::logic_error`。

**Q：`Run()` 和 `RunAsync()` 有什么区别？**
`Run()` 在调用线程同步跑完；`RunAsync()` 提交到线程池后立即返回，需要收敛时用 `Wait()`。

**Q：`RunAsync()` 返回后回调一定还没触发吗？**
不能这么假设。`RunAsync()` 只保证“不等待执行完成”，worker 可能在返回前后就开始跑。

**Q：步骤失败了怎么表达？**
在步骤函数里抛异常。库会把它转为 `Failed`，并让下游 `Skipped`。

**Q：一张大图想中途放弃？**
目标语义是在任意线程或回调里调用 `Cancel()`；该能力阶段 3 实现。

**Q：为什么接口全是 virtual、没有成员？**
这是抽象接口设计：业务只依赖契约，具体实现（以及它的线程池、数据结构）藏在库内部，便于替换和演进而不用改公共头。
