# 图片处理流水线 SDK —— 训练文档

> 版本 1.0 ｜ 目标读者：有 C++ 基础、想系统练习 SDK 接口设计的中级开发者
> 预计周期：2～3 周（业余时间）/ 5～7 个工作日（全职）
> 代码量上限：业务代码 ≤ 10k 行（含测试）

## 1. 训练目标

完成本训练后，你应该能够：

- 区分同步/异步回调的体感与契约，并能用测试证明自己声明的契约。
- 在“有明确拓扑顺序”的业务里，正确地把顺序交给调度器、把通知交给回调，不让回调承载编排。
- 组合使用“静态工厂 + 抽象接口 + Impl”与 Pimpl，做到契约隔离与内部演进互不干扰。
- 处理异步回调的生命周期、取消、错误传播、重入，并通过 ASan/TSan。
- 写出一份可被业务方信任的接口契约文档，而不只是能跑的代码。

## 2. 前置要求

- 熟悉 C++17（`std::function`、`std::thread`、`std::mutex`、`condition_variable`、`unique_ptr`、`shared_ptr`）
- 用过 CMake
- 知道什么是 ASan / TSan
- 不需要提前懂 DAG 调度、线程池实现

## 3. 业务场景

业务方拿到一张原图，要按固定步骤处理：

```text
加载 → 解码 → 缩放 → 加水印 → 编码 → 保存
```

约束：

- 步骤之间有严格先后（解码必须在缩放前，编码必须在保存前）
- 业务方希望每完成一步收到一次通知（用于进度条、日志、埋点）
- 一张图可能很大，用户可能中途点“取消”
- 某一步失败，下游步骤应跳过，并各自收到“已跳过”通知

SDK 要提供的，就是让业务方声明步骤和依赖、注册通知、触发执行的能力。

## 4. 对外接口契约（v1 头文件骨架）

这是你第一天就要定下来的东西，后续所有阶段都基于它演进。注释里的每一条都要能在测试里找到对应用例。

```cpp
// include/image_pipeline.h
#pragma once
#include <cstdint>
#include <functional>
#include <memory>
#include <string>

namespace imgpipe {

using StepId = std::uint64_t;

enum class StepState {
    Pending,     // 尚未开始
    Running,     // 正在执行
    Succeeded,   // 执行成功
    Failed,      // 执行失败
    Skipped,     // 因上游失败/取消而跳过
    Cancelled,   // 被显式取消
};

struct Error {
    int code = 0;
    std::string message;
    bool ok() const { return code == 0; }
};

// 通知回调。必须满足：
// 1) 可能在任意库内线程触发，业务需自行保证线程安全
// 2) 同一 StepId 的通知保证串行，且顺序为 Pending → Running → (Succeeded|Failed|Skipped|Cancelled)
// 3) 上游 Step 的 Succeeded 通知一定先于下游 Step 的 Running 通知
// 4) 回调应短小非阻塞；回调内允许调用 Cancel()，但不允许调用 AddStep/AddDependency
// 5) 回调抛出的异常会被库捕获并转为 Failed，不会穿透
using Listener = std::function<void(StepId, StepState, const Error&)>;

struct Config {
    std::uint32_t maxConcurrency = 2;  // 同时执行的 Step 上限
};

class Pipeline {
public:
    // 静态工厂：唯一构造入口
    static std::unique_ptr<Pipeline> Create(const Config& cfg = {});

    // 测试专用：返回一个不启动真实线程的 Mock 实现
    static std::unique_ptr<Pipeline> CreateForTest();

    virtual ~Pipeline() = default;

    // ---- 构图阶段（Run 之前调用）----
    virtual StepId AddStep(std::string name, std::function<void()> fn) = 0;
    virtual void   AddDependency(StepId downstream, StepId upstream) = 0;

    // ---- 通知 ----
    // 传 nullptr 表示注销。注销返回后，库保证不再触发新的回调；
    // 已在执行中的回调允许跑完。
    virtual void SetListener(Listener listener) = 0;

    // ---- 执行 ----
    // 异步：立即返回。返回后回调可能尚未触发。
    // 同一 Pipeline 实例同时只允许一次 Run；重复调用返回 false。
    virtual bool Run() = 0;

    // 取消：已 Running 的 Step 允许完成；未开始的 Step 转为 Cancelled 并触发通知。
    // 可在任意线程、任意时刻调用，包括在回调内部。
    // 返回后不保证回调已全部结束，但保证不再有新回调触发。
    virtual void Cancel() = 0;

    // 阻塞直到当前 Run 收敛（无论成功/失败/取消）。
    // 若未调用过 Run，立即返回。
    virtual void Wait() = 0;
};

} // namespace imgpipe
```

> **契约检查点：** 上面 5 条回调契约、Run 的异步语义、Cancel 的幂等性，每一条都要在阶段 2/3 有对应测试。接口先冻结，实现再演进——这是本训练的核心纪律。

## 5. 分阶段任务

### 阶段 1：同步内核（3～4 天）

**目标：** 先把“执行顺序正确”做对，故意用同步回调，让业务体感是阻塞的。

**要做**

- 实现 `PipelineImpl`（继承 `Pipeline`），内部用一个 `std::map<StepId, Step>` 存图
- `Run()` 阻塞到整张图跑完，回调在 `Run()` 的调用线程执行
- 单线程串行执行，按拓扑序
- 拓扑排序算法自选（Kahn / DFS），必须有环检测，有环时 `Run()` 返回前通过回调报 `Failed`
- `AddDependency` 时校验上下游存在、无自环

**不做**

- 不做线程池
- 不做取消（Cancel 可空实现）
- 不做 Pimpl

**验收**

- [ ] 6 步骤链式图，`Run()` 返回后所有回调已收到，顺序严格等于拓扑序
- [ ] 菱形图（A→B、A→C、B→D、C→D），D 的 Running 在 B、C 的 Succeeded 之后
- [ ] 有环图 `Run()` 不死循环，报错
- [ ] 单测不依赖任何线程原语，纯顺序执行

> **这一阶段的隐藏训练点：**
> 你会第一次面对“回调里能不能调 AddDependency”的问题。答案是不能——如果回调在 `Run()` 里执行，业务方在回调里改图会破坏正在遍历的结构。所以头文件必须写清楚：构图与执行是两阶段，执行开始后禁止改图。这个约束在阶段 2 变成并发了会更重要。

### 阶段 2：异步化（3～4 天）

**目标：** 把 `Run()` 改成立即返回，回调改到 worker 线程，业务代码一行不改。

**要做**

- 引入内部线程池（`maxConcurrency` 控制并发）
- `Run()` 投递可执行 Step 到线程池后立即返回
- Step 完成时唤醒依赖它的下游 Step（通过一个 ready 队列 + 条件变量）
- `Wait()` 阻塞到所有 Step 进入终态
- 严格实现头文件里的 5 条回调契约

**关键设计决策（写进 design.md）**

- 回调在哪个线程触发？ worker 线程直接调，还是专用通知线程？
  - worker 直接调：延迟低，但回调慢会拖慢 worker
  - 专用通知线程：需要额外的有序队列，但能隔离回调对调度的影响
  - 建议：worker 直接调，但在文档中声明“回调必须短小非阻塞”，并接受这个约束。选专用线程的话，要证明它能保证“同 Step 串行”。
- 回调保序怎么保证？ 同一个 Step 的 Pending/Running/Succeeded 可能在不同线程触发，怎么保证顺序？
  - 建议：状态变化和回调触发在同一把锁内完成投递，或者用每 Step 一个序号 + 单通知线程
- `Run()` 的幂等性：重复 `Run()` 返回 false，状态怎么管？

**验收**

- [ ] 有测试证明 `Run()` 返回早于任一回调触发（用 `std::atomic` + 短 sleep 或 `condition_variable` 证明）
- [ ] 有测试证明同一 Step 的回调不并发（回调里置标志，进回调时 assert 未置位）
- [ ] 有测试证明上游 Succeeded 通知先于下游 Running 通知（回调里打时间戳 + 全局顺序校验）
- [ ] 有测试证明 `maxConcurrency=1` 时同一条链严格串行
- [ ] 所有测试在 TSan 下通过

> **这一阶段的隐藏训练点：**
> 你会亲手验证“用不用线程池，和是不是异步回调，是两件事”。阶段 1 用 `Run()` 阻塞也能做同步回调；阶段 2 引入线程池后，如果 `Run()` 还是阻塞到所有回调完成，业务体感依然是同步的——“异步”是 `Run()` 立即返回 + 回调稍后到达，不是线程池本身。

### 阶段 3：取消、错误、生命周期（3～4 天）

**目标：** 把跨线程异步回调最难的部分吃完。

**要做**

- `Cancel()`：已 Running 的 Step 允许完成，Pending 转 Cancelled 并发通知
- 上游 Failed / Cancelled → 下游 Skipped，每个跳过也发通知
- `Cancel()` 幂等，可在回调内调用，不引入死锁
- `SetListener(nullptr)` 返回后不再触发新回调，但允许正在执行的回调跑完
- 析构函数必须等“回调不可能再触发”后才返回（避免 use-after-free）
- 回调抛异常 → 捕获并转 Failed，不穿透 worker

**必踩的坑（每个都要在 design.md 里写你怎么解决的）**

1. **回调里调 `Cancel()`**：如果你在 `Cancel()` 里持锁遍历 Step，而回调也在持锁期间被调用 → 死锁。解法：不要在持锁期间调用用户回调，把通知事件压进队列，锁外投递。
2. **`SetListener(nullptr)` 时回调正在执行**：`std::function` 被销毁的瞬间正在被调用 → UB。解法：Listener 用 `shared_ptr<Listener>` 持有，调用时拷贝一份；或者用“标记 + 引用计数”保证正在执行的回调持有一份强引用。
3. **析构时 worker 还在回调**：析构函数如果不等待就释放 Impl → use-after-free。解法：析构里 `Cancel()` + `Wait()` + join 所有 worker，再释放。
4. **回调抛异常穿透**：worker 线程里 `std::terminate`。解法：回调外层包 try/catch，异常转 Failed 发通知。

**验收**

- [ ] 压测：随机时刻 `Cancel()` × 1000 次，无崩溃、无 use-after-free
- [ ] 测试：`SetListener(nullptr)` 后统计回调计数不再增长
- [ ] 测试：回调内调 `Cancel()`，`Wait()` 正常返回，无死锁
- [ ] 测试：回调抛异常，`Wait()` 正常返回，该 Step 状态为 Failed
- [ ] 析构场景 ASan 全绿
- [ ] 并发场景 TSan 全绿

### 阶段 4：抽象 + Pimpl 组合（2～3 天）

**目标：** 把“静态工厂 + 抽象接口 + Impl”和 Pimpl 组合起来，验证内部演进不影响对外头文件。

**要做**

- 对外只暴露 `include/image_pipeline.h`（已冻结）
- `src/pipeline_impl.h` 里 `PipelineImpl : public Pipeline`，内部持有 `struct Impl; std::unique_ptr<Impl> impl_;`
- `PipelineImpl::Impl` 承载全部数据结构和线程原语
- 实现 `CreateForTest()`：返回一个 `MockPipeline`，不启动线程，`Run()` 同步跑完、回调在调用线程触发
- 断言：`sizeof(Pipeline)` 对外不可见（抽象类无成员）；改 Impl 内部成员，`image_pipeline.h` diff 为 0

**验收**

- [ ] grep 公共头文件，除 `struct Impl` 外无任何私有成员（抽象接口本来就没有，但要确认没泄漏）
- [ ] 写一个业务单测，用 `CreateForTest()` 跑完整流程，不依赖任何 sleep
- [ ] 在 Impl 里加一个新成员（比如 `std::atomic<uint64_t> callbackCount_` 统计回调次数），重新编译，公共头文件 diff 为 0
- [ ] 写一段 100 字说明：为什么对外用抽象接口、对内再套 Pimpl，而不是只选一个

> **这一阶段的隐藏训练点：**
> 你会亲手验证两者不是替代关系。抽象接口解决“多实现 / Mock / 契约隔离”；Pimpl 解决“内部数据结构和依赖演进不污染头文件”。对外抽象、对内 Pimpl，是商用 SDK 的常见组合。

## 6. 设计决策清单（必须写进 design.md）

每个决策写三部分：选项 → 你的选择 → 理由与代价。字数不限，但要有取舍，不要只写“我选 A”。

1. `AddStep` 的 fn 签名为什么用 `std::function<void()>`？为什么不用 `std::function<Result()>` 或模板？失败怎么表达？
2. 回调在 worker 线程直接触发，还是专用通知线程？各自对延迟、顺序、背压的影响。
3. 同一 Step 的回调保序，你怎么实现？锁内投递 vs 序号+单线程。
4. `Run()` 是否可重入？不可重入时返回 false 还是抛异常？为什么？
5. `Cancel()` 对已 Running 的 Step 语义：允许完成还是强制中断？为什么？
6. 回调抛异常：转 Failed 还是直接终止？转 Failed 后要不要再触发一次 Failed 通知（会不会重复）？
7. `SetListener(nullptr)` 后，正在执行的回调是否允许继续？你用什么机制保证 `std::function` 不被提前销毁？
8. 析构函数里怎么保证“不再有回调”+“不阻塞太久”？
9. 为什么对外用抽象接口、对内套 Pimpl？如果只选一个，你选哪个，为什么？
10. 回调里禁止 `AddStep` / `AddDependency`，你怎么运行时检测并给出清晰错误，而不是靠文档约定？（提示：一个 `building_` 原子标志）

## 10. 常见“看起来做完了但其实没做对”的信号

如果你出现下面任一情况，回去对应阶段重做：

| 信号 | 说明 | 回看 |
| --- | --- | --- |
| `Run()` 里 join 所有 worker 才返回 | 你做的还是同步，不是异步回调 | 阶段 2 |

## 13. 未来展望

当前实现已经覆盖“建图 → 同步/异步执行 → 取消 → 生命周期 → C API”，下面是继续演进的方向，按“收益/成本”大致排序。

| 方向 | 收益 | 主要成本 |
| --- | --- | --- |
| 协作式取消（`std::stop_token`） | 长步骤能更快响应取消，而不是只能等它跑完 | 需要改 `Step` 契约，业务步骤配合检查 |
| 专用通知线程 | 慢回调不拖住 worker，通知顺序更容易保证 | 多一个有序队列和线程，`Cancel`/析构要一起改 |
| 可观测性 | 每步耗时、并发度、队列深度、回调耗时；便于定位瓶颈 | 需要埋点结构和导出方式（日志/指标） |
| 调度器增强 | 优先级、超时、重试、按资源限流 | 入度逻辑之外再加一层策略，复杂度上升 |
| 错误模型演进 | `Result`/`std::expected` 版本，错误分类、重试 | 改冻结契约，每个步骤都要处理返回值 |
| C API / ABI 版本化 | 结构体带 `size`、能力查询、语义化版本 | 需要长期兼容策略和回归测试 |
| 测试与工具 | Clang TSan、随机 DAG 生成、fuzz、超时/饥饿用例 | 需要额外 CI 环境和运行时间 |
| 性能优化 | 对象池、批量提交、减少锁竞争 | 先有基准测试，否则容易过度优化 |
| 功能扩展 | 子流水线、动态图、插件式步骤 | 会破坏“构图后冻结”的简单模型 |

建议顺序：

1. 先把 **TSan（Clang）** 补上，这是当前最大的验证缺口
2. 再做 **协作式取消**，它对真实图片处理的体验提升最直接
3. 有了真实业务压测后，再决定要不要 **通知线程** 和 **调度器增强**
4. `Result`/`expected` 和 C API 版本化，等接口真要对外长期发布时再动

> 原则：先补验证，再谈扩展；不要在缺少压测和工具的情况下继续堆功能。
