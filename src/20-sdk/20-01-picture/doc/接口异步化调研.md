# 接口异步化调研

> 范围：C++ SDK 中“同步/异步执行接口”的常见实现方式，以及对本项目 `imgpipe` 的选型建议。
> 结论先行：业界没有把调度循环留在调用方线程的异步实现；主流是**执行资源（Executor/ThreadPool）+ 完成事件驱动 + 可等待的收敛点**。

## 1. 四种主流范式

### 1.1 Executor + Future

代表项目：

- **cpp-Taskflow**：`tf::Taskflow` 描述 DAG，`tf::Executor` 是线程池；`executor.run(taskflow)` 返回 Future，`wait()` 收敛，`cancel()` 取消。
- **LLVM `llvm::ThreadPool`**：`async(f)` 返回 `std::future`，`wait()` 收尾。
- **Folly**：`Future` / `SemiFuture` + `Executor`，`then()` 串联后续，`wait()`/`get()` 收敛。
- **`std::async`**：返回 `future`，`get()` 阻塞。

机制：提交任务返回 future；完成时 `promise.set_value`；等待方 `future.wait()`。适合需要组合、链式、超时的场景。

### 1.2 Event Loop + 完成回调

代表项目：

- **Boost.Asio**：`async_xxx(handler)` 立即返回；`io_context::run()` 驱动事件循环；`post()` 投递任务；`strand` 保证同一对象回调串行；`thread_pool` 提供执行线程。
- **libuv / Node.js**：主线程跑事件循环；阻塞操作丢线程池，完成后回调回到循环线程。
- **gRPC C++**：异步接口用 completion queue，`AsyncNext()` 取完成事件。

机制：一个（或少数几个）事件循环线程 + 完成队列；worker 只做阻塞工作。
注意：Asio 的 `run()` 是**调用方主动驱动的循环**，只负责事件分发，不等于“在调用线程里跑业务调度”。

### 1.3 Task Graph / Dataflow

代表项目：

- **oneTBB Flow Graph**：节点 + 边；上游完成发 `continue_msg`，下游收到才执行；`wait_for_all()` 收敛。
- **cpp-Taskflow**：依赖由拓扑决定，内部工作窃取调度。
- **Airflow / Prefect / Dagster**：独立 scheduler 持续计算 ready 任务，交给 executor 执行。

机制：图推进由“完成事件”驱动，而不是调用方循环。Kahn 的入度递减就是它的最小实现。**与本项目形态最接近。**

### 1.4 ThreadPool + Sequence / Strand

代表项目：

- **Chromium**：`TaskRunner` 投递任务，`SequencedTaskRunner` 保证同一 sequence 顺序执行，线程池提供并行；`WaitableEvent` 阻塞等待。
- **Asio `strand`**：同一 strand 上的回调串行。

作用：解决“同一对象顺序、不同对象并行”，对应本项目的“同一 Step 通知串行、不同 Step 可并发”。

### 1.5 趋势：协程

C++20 `co_await` + executor（Asio `awaitable`、cppcoro）、Rust tokio。写法接近同步代码，但依赖运行时与执行器，超出当前训练范围。

## 2. 横向对照

| 项目/范式 | 接口形态 | 谁推进下一步 | 完成信号 | 等待方式 | 取消 |
| --- | --- | --- | --- | --- | --- |
| Taskflow | `run()` 返回 Future | 完成事件 + 调度器 | Future | `future.wait()` | `future.cancel()` |
| LLVM ThreadPool | `async()` 返回 future | 线程池 | promise | `future.wait()` | 无细粒度取消 |
| Folly | Future/Executor | 完成回调链 | promise | `wait()/get()` | 取消状态 |
| Asio | `async_xxx(handler)` | `io_context::run()` | 回调 | `future` / `run()` 返回 | `cancellation_slot` |
| TBB Flow Graph | 节点/边 | `continue_msg` | 消息 | `wait_for_all()` | 节点级取消 |
| Chromium | `PostTask` | 任务序列 | 回调/`WaitableEvent` | `Wait()` | task 取消标志 |
| Airflow | DAG + scheduler | 独立 scheduler | 任务状态 | 外部轮询 | 任务状态 |

## 3. 共性设计原则

1. **调度与执行分离**：谁决定下一步（调度器）与谁真正执行（线程池）是两件事。
2. **推进由完成事件驱动**：上一任务完成才提交下一批，调用方不持有业务循环。
3. **统一完成信号**：回调、future/promise、消息、completion queue 四选一，不要混用。
4. **显式收敛点**：`future.wait()`、`wait_for_all()`、`latch`、未完成计数 + 条件变量。
5. **取消是一等公民**：cancel token / stop flag / future.cancel()。
6. **串行靠 strand/sequence/锁**，不要靠“碰巧只有一个线程”。
7. **明确回调所在线程**：worker 线程还是事件循环线程；业务侧据此决定是否加锁/转发。

## 4. 映射到 imgpipe

| imgpipe 概念 | 业界对应 |
| --- | --- |
| `RunAsync()` | `executor.run(graph)` / `post()` |
| worker 完成一步后减入度、提交下游 | TBB `continue_msg` / Taskflow 依赖推进 |
| `Wait()` | `future.wait()` / `wait_for_all()` / latch |
| `Cancel()` | cancel token / future.cancel() / stop flag |
| `Listener` | completion callback |
| 同一 Step 通知串行 | strand / sequenced task runner |
| 跨线程的未完成计数 | atomic/latch + condition_variable |

### 已采用方案（阶段 2 已落地）

采用 **1.3 Task Graph 的事件驱动模型**，执行器使用 Boost.Asio `thread_pool`：

- `RunAsync()`：先做静态环检测，再把入度为 0 的节点提交线程池，立即返回；
- worker 执行一步：发 `Pending → Running → 终态`，锁内减下游入度、更新未完成计数，锁外提交新 ready 节点；
- `Wait()`：在“未完成计数归零”对应的条件变量上等待；
- `Run()`：保留“调用线程执行”的同步语义，与异步路径互不影响；
- 失败：下游递归标记 `Skipped`，未完成计数照常递减，避免 `Wait()` 卡死；
- `Cancel()`：阶段 3 实现。

实现要点：

- 线程池懒创建，大小取 `Config::maxConcurrency`；
- 回调在 worker 线程触发，业务侧需线程安全；
- 锁只保护调度状态（入度、已处理集合、未完成计数），持有锁时不调用用户代码；
- 上游 `Succeeded` 在提交下游之前发出，天然满足通知顺序契约。

## 5. 可演进方向

- `RunAsync()` 返回 `RunHandle`/`Future`（含 `wait()`/`cancel()`），`Wait()` 保留兼容。
- 回调放入专用通知线程，隔离慢回调。
- 引入协程接口，但需先稳定 executor 抽象。
