# 12-05-resume —— 单线程断点续传

对应 `downloader-roadmap.md` 阶段 4。

**目标**：下载到一半 Ctrl+C，重跑同一条命令能接着下，最终文件和一次性完整下载的 MD5 一致。

**不做**：多线程分块（阶段 5）、崩溃一致性日志（阶段 6）、重试与调度（阶段 7）。
这一阶段只有一个连接、一个线程、一个写入位置。**先把续传在单线程下做对**——
跳过这一步直接上多线程，你会同时调试「续传逻辑错」和「并发写盘错」两类 bug，
而这两类 bug 的症状是一样的：文件大小对、内容是错的、程序不报错。

---

## 1. 这一阶段真正的难点

不是「怎么发 `Range: bytes=N-`」——那是一行字符串拼接。难点有三个：

| 难点 | 本质 |
| --- | --- |
| **断点是多少** | 本地已有 N 字节，这个 N 从哪读？能信吗？ |
| **服务端上的文件还是不是原来那个** | 你有 5 MB 旧文件的前半段，服务端换了新版本，接着下 = 拼出一个两个版本混合的垃圾文件，**校验和之外没有任何信号会告诉你** |
| **失败要留下可恢复的状态** | 中断后磁盘上剩下的东西，必须能让下一次运行正确判断「下到哪了」 |

第二条是续传的正确性核心。HTTP 给了你一个头解决它：`If-Range`。

---

## 2. 断点从哪来：文件大小就是唯一真相

**不要**为了记录进度另开一个 `.progress` 计数文件，也**不要**信任内存里累计的
「写回调收到了多少字节」——单线程阶段，`.part` 文件的实际大小**就是**断点。

理由：任何独立于文件本身的计数都可能和实际落盘的字节数不一致。
`std::ofstream` 有用户态缓冲，OS 有页缓存，进程被 Ctrl+C 杀掉时缓冲区里的数据直接蒸发。
如果你的计数器说「下了 5 MB」但文件里只有 4.9 MB，续传就会从 5 MB 处接着写——
中间那 100 KB 变成了**空洞**（Windows 上 seek 越过末尾再写，中间填 0）。
文件大小对得上，内容是错的。

反过来，用文件大小当断点，缓冲区丢数据只会导致**重下一小段**——保守，但永远正确。
这个「宁可重下，不可漏下」的性质，是阶段 6 引入 journal 之后仍然要保持的不变式。

> [Tips] 阶段 5 会打破这个前提
> 多线程分块时，一个文件里有 N 个不连续的写入位置，「文件大小」不再能表达进度。
> 那时才需要 journal。现在别提前发明它。

**要想清楚**：

- 用什么读文件大小？`std::filesystem::file_size` / `seekg(0, ios::end)` + `tellg` / `_stat64`——
  哪个在 Windows 上对 >4 GB 文件是安全的？（`tellg` 返回的 `std::streamoff` 是多少位？）
- `.part` 不存在 = 断点 0，和 `.part` 存在但为 0 字节，代码路径应该一样吗？

## 3. 打开文件的姿势（Windows 上的两个必死坑）

### 3.1 少一个 `std::ios::binary`，文件必坏

MSVC 的文本模式会把写出的 `0x0A` 翻译成 `0x0D 0x0A`。下载二进制文件时，
每遇到一个 `0x0A` 字节就多写一个字节：**文件变大、内容错位、`Content-Length` 对不上**。
`test_100m.bin` 里 `0x0A` 大概占 1/256，也就是文件会胖 0.4%——
大到能发现，但你第一反应绝对不会怀疑到 `ios::binary` 上。

### 3.2 `app` 和 `ate` 不是一回事

| 模式 | 语义 |
| --- | --- |
| `ios::app` | **每一次**写都强制落到当前文件末尾，`seekp` 对写入位置无效 |
| `ios::ate` | 打开后把指针**移到**末尾，之后 `seekp` 正常起作用 |
| `ios::out`（单独） | **截断**文件为 0 |
| `ios::out \| ios::in` | 不截断，可读可写 |

这个区别在本阶段有实际后果：服务端返回 200（见第 5 节）时你必须**丢弃本地进度、从 0 重写**。
如果流是用 `app` 打开的，你没法退回去——只能关掉重开。
先决定「一个流打开后能应付所有分支」还是「先判分支再决定怎么打开」，再写代码。

## 4. 请求长什么样

```
GET /ranged/test_100m.bin HTTP/1.1
Host: 127.0.0.1:8000
Range: bytes=5242880-              <- 开区间，从第 5242880 字节到结尾
If-Range: "6400000-68af1c20"       <- 阶段 3 存在 DownloadPlan.etag 里的值，原样带引号
```

`If-Range` 的服务端语义：

- **validator 匹配** → 正常处理 `Range`，返回 `206` + 你要的那一段
- **validator 不匹配** → **忽略 `Range`**，返回 `200` + 整个新文件

一个头搞定「校验 + 回退」，不需要你先发一次条件请求再判断——但代价是
**你的代码必须能处理返回 200 的情况**，而不是把 200 当成异常抛掉。

> [Tips] `If-Range` 的值不要自己加引号
> ETag 的引号是值的一部分。`DownloadPlan.etag` 里存的应该已经是 `"abc123"`（含引号）
> 或 `W/"abc123"`。拼头的时候直接 `"If-Range: " + *plan.etag`。
> 如果你在阶段 3 把引号剥掉了，现在就得补回来——先去 `ResponseHeaders` 里确认存的是哪种。

**没有 ETag 怎么办**：退回 `Last-Modified` 的日期，但先看第 8 节第 1、2 题。
两个都没有 → 服务端没给你任何 validator，续传是**不安全**的。
这时候的策略选择（照样续 / 拒绝续传从头下 / 提示用户）请自己定，并写进 `## 已知缺口`。

## 5. 响应分档表（本阶段的核心状态机）

拿到响应后，先看状态码，再看 `Content-Range`。**在验证通过之前，一个字节都不许落盘。**

| 状态码 | 含义 | 动作 |
| --- | --- | --- |
| `206` + `Content-Range` first == N | 正常续传 | 追加写，直到 total |
| `206` + first ≠ N | 服务端给了**别的**区间 | **立刻中止**。写下去就是错文件，且不会有任何报错 |
| `206` + 无 `Content-Range` | 协议违规 | 中止 |
| `200` | If-Range 不匹配（文件变了），或服务端根本忽略 Range | 丢弃本地进度：截断 `.part` 到 0，从头写 |
| `416` | Range 不可满足 | 见下，**先别当错误** |
| `404` / `410` | 资源没了 | 中止。`.part` 删还是留？自己定策略 |
| `5xx` | 服务端炸了 | 中止，保留 `.part`（下次还能续） |

### 5.1 `416` 是好消息还是坏消息

`Range: bytes=N-` 里的 N **必须小于**当前资源长度，否则服务端返回 `416`。
所以当你已经下完（N == total）再跑一次，得到的就是 `416`。
这是**正常完成**，不是错误。

区分方法：416 的响应体头里有

```
Content-Range: bytes */1234567
                     ^ 星号，没有区间；斜杠后是当前总长
```

拿这个 total 和本地 `.part` 大小比：

- 相等 → 已经下完了，直接走 rename 收尾
- 本地 **大于** total → 本地文件比服务端的还长，说明文件换了（且变短了）。丢弃重下
- 本地小于 total → 你发的 N 有问题，或者服务端行为异常。中止并报错

> [Tips] `ContentRange::parse` 现在解析不了 `bytes */N`
> 12-04 的 `## 7. 已知缺口` 第 1 条记着这个：`Probe.cpp` 当时是绕过去的（直接抠斜杠后的数字）。
> 这一阶段你会**第二次**撞上它。两条路，挑一条，别再绕第三次：
> 扩展 `ContentRange::parse` 支持 `*`（然后回头删掉 `Probe.cpp` 的绕行），
> 或者在 12-05 里写一个专门的 `parse_unsatisfied_range`。

### 5.2 `206` 但区间不对，为什么必须中止而不是「调整一下」

因为你**无法判断**服务端是「理解了但给错了」还是「文件已经换了」。
唯一安全的动作是把这次响应整个丢掉。这条铁律在阶段 5 会变得更重要——
四个线程各写各的偏移，一个线程信了错区间，产出的坏文件没有任何症状。

**校验清单**（每次 206 都要过一遍）：

1. `Content-Range` 存在且能解析
2. `first == 本地已有字节数`
3. `total` 存在，且和 `DownloadPlan.total_size` 一致（不一致 = 文件换了）
4. `last == total - 1`（你要的是「到结尾」）

## 6. `.part` 与原子完成

写 `目标名.part`，**全部字节到齐后**再 rename 成 `目标名`。

为什么不直接写目标文件名：用户（和你自己的程序）无法区分「下完了」和「下了一半」。
一个 90% 的 `.mp4` 双击也能播，前 90% 是好的——这类 bug 极难归因。

**完成判定**：`curl_easy_perform` 返回 `CURLE_OK` **不等于**下载完整。
连接可能在传到一半时被对端正常关闭。判定条件是
**本地文件大小 == `DownloadPlan.total_size`**，这一条不满足就别 rename。

### Windows 上的 rename

| 做法 | 目标已存在时 |
| --- | --- |
| `std::rename`（C 库） | **失败**（POSIX 上会覆盖——跨平台代码在这里行为不一致） |
| `std::filesystem::rename` | MSVC 走 `MoveFileExW` + `MOVEFILE_REPLACE_EXISTING`，覆盖 |
| `MoveFileExW` 手写 | 自己控制标志位 |

还要先想好：**目标文件已存在时的策略是什么**？覆盖 / 加序号（`file (1).bin`）/ 报错退出。
挑一个，写进 readme，别让它成为运行时才发现的行为。

另外，rename 之前记得**先关掉文件流**。Windows 的文件是独占句柄，
流还开着的时候 rename 会失败，而且 `std::filesystem::rename` 抛的异常信息不会告诉你原因是这个。

## 7. 中断：怎么优雅地被打断

Ctrl+C 默认直接杀进程——`ofstream` 的析构不跑，缓冲区数据丢。
按第 2 节，这**不会**产生错误的文件，只会损失一小段进度。所以「什么都不做」是可接受的起点。

但阶段 2（`12-03-easy`）已经写过进度回调返回非 0 取消传输的机制，这里应该用上：

1. 装一个信号处理器（`signal(SIGINT, ...)` 或 Windows 的 `SetConsoleCtrlHandler`），
   只做一件事：把一个 `volatile std::sig_atomic_t` / `std::atomic<bool>` 置位
2. 进度回调每次被调用时检查这个标志，置位就返回非 0
3. `curl_easy_perform` 返回 `CURLE_ABORTED_BY_CALLBACK`
4. 正常走到收尾代码：flush、close、**不** rename、退出码标记为「用户取消」

> [Tips] 信号处理器里能做的事极少
> 不能 `new`、不能加锁、不能 `std::cout`。只能给 `volatile sig_atomic_t` 赋值。
> 这也是为什么真正的退出逻辑要放在进度回调里——那是普通线程上下文。

**退出码要分档**，验收脚本要靠它判断：完成 / 用户取消 / 网络失败 / 协议错误（206 区间不对这种）。

## 8. 必须能回答的问题

前三题来自 roadmap，后面几题是这一阶段实际会撞上的。
**把你的答案写进这个 readme 的 `## 我的答案` 一节**——半年后回头看，这些比代码值钱。

1. `If-Range` 里可以放 `Last-Modified` 的日期吗？和放 ETag 相比有什么风险？
   （提示：HTTP-date 的精度是**秒**。一个文件在同一秒内被改了两次会发生什么？
   再想想 RFC 9110 为什么要求服务端只在「日期比响应的 `Date` 头早至少 1 秒」时才把它当强 validator）
2. 弱 ETag（`W/"xxx"`）能用于 `If-Range` 吗？为什么？
   （提示：弱 validator 的语义是「语义等价」而非「字节相同」。续传要的是哪一种？）
3. 断点在文件最后一个字节之后（已经下完）时，`Range: bytes=N-` 得到什么响应？
   `416` 意味着什么，怎么和「真的出错了」区分开？
4. 为什么不能用「写回调累计收到的字节数」当断点，而必须用文件的实际大小？
   什么情况下这两个数会不一致？
5. `.part` 用 `ios::app` 打开，在「服务端返回 200 要从头重写」这条分支上会出什么问题？
6. 服务端返回 `206`，但 `Content-Range` 的 first 比你要的 N **小**（多给了一段重叠数据），
   如果你直接追加写会发生什么？文件大小会对吗？内容呢？
7. `CURLOPT_RESUME_FROM_LARGE` 能替你设 `Range` 头。本阶段建议自己拼头，为什么？
   （至少三个角度：学习目的；和 `If-Range` 的配合；`curl_easy_reset` 之后它的残留值；
   以及它和你手动加的 `Range:` 头同时存在时谁赢）
8. 真实下载**不能**设 `CURLOPT_TIMEOUT`（阶段 3 的探测请求设了）。为什么？
   那用什么来检测「连接卡死了」？（提示：`CURLOPT_LOW_SPEED_LIMIT` / `LOW_SPEED_TIME`）
9. 续传时进度回调的 `dlnow` / `dltotal` 是**本次连接**传的量，还是含已下载的 N？
   自己打印一次实测——进度条显示对不对全看这个。

## 9. 复用与边界

各专题目录之间**没有任何 target 依赖**：`12-04-probe` 是纯 `add_executable`，
`12-05-resume` 只链 `CURL::libcurl`，平铺布局（`.h` 和 `.cpp` 都在本目录，不分 `include/src`）。

阶段 3 那些东西——`CurlEasy` / `CurlSlist` / `GlobalCurlGuard` / `ResponseHeaders` /
`ContentRange` / `FilenameResolver` / `Probe` / `DownloadPlan` / `ProbeContext`——
需要哪块就从 `12-04-probe` 拿一份过来，或者重写。
**流程不变**：探测出 `DownloadPlan` → 下载器吃 `DownloadPlan`。

> [Tips] 拿过来就是一次分叉
> 复制进 12-05 之后再改 `ContentRange::parse`，12-04 那边不会跟着变，
> 12-04 的单测也测不到你的新版本。改之前先分清楚：
> 修的是**阶段 3 就存在的 bug**（那么两边都要改，或者认下 12-04 是历史快照），
> 还是**阶段 4 才需要的新能力**（那就只改这边，并在下面的「已知缺口」里记一笔）。

### 三种 mode 在本阶段各走哪条路

| `TransferMode` | 阶段 4 的处理 |
| --- | --- |
| `RangedParallel` | 本阶段**按单线程续传**跑（并行是阶段 5 的事）。这是主路径 |
| `SingleResumable` | 见下——这个名字有坑 |
| `StreamingChunked` | 长度未知、不可续传。只能从头下，`.part` 存在就删掉重来。要不要支持，自己定 |
| `Unknown` | 直接报错退出 |

> [Tips] 12-04 已知缺口第 2 条现在到期了
> `SingleResumable` 在 `supports_range == false` 时**名不副实**——服务端不支持 Range，
> 断了根本续不上。阶段 4 必须把这一档拆开：可续 / 不可续。
> 改 `TransferMode` 枚举（会动到 12-04 的代码和测试），还是在 12-05 里另立一个内部判断？
> 挑一条，理由写进 readme。

### 不要碰的东西

- **`CURLOPT_ACCEPT_ENCODING` 保持关闭**（12-04 readme 4.7 已论证）。开了压缩，
  `Content-Length` 描述的是压缩后的长度，而 Range 是对**未压缩**字节计的，
  续传的偏移会全线错位。
- `CURLOPT_NOSIGNAL = 1L` 现在就设好，阶段 5 上多线程时不用回头补。

```bash

cmake --preset msvc
cmake --build --preset msvc
```

产物落在 `12-05-resume/build/bin/`（沿用各专题的 `EXECUTABLE_OUTPUT_PATH` 约定）。

建议的命令行形态（自己定，这里只是起点）：

```
12-05-resume <url> [-o <输出文件>] [--limit-rate <字节/秒>] [-v]
```

`--limit-rate` 建议**自己实现**（`CURLOPT_MAX_RECV_SPEED_LARGE`），
这样验收时不需要给测试服务器加限速——见下一节。

### 测试服务器

`testdata/probe_server.py` 现有路由：

| 路由 | 行为 |
| --- | --- |
| `/ranged/<file>` | 正常支持 Range，带 ETag |
| `/ignore/<file>` | 忽略 Range，永远 200 + 全量 |
| `/liar/<file>` | 声明 `Accept-Ranges: bytes` 但实际忽略 Range |
| `/redirect/<file>` | 302 到 `/ranged/<file>` |
| `/chunked` | chunked，无 `Content-Length` |
| `/empty` | 零长文件 |
| `/cd` | 带 `Content-Disposition` 的中文文件名 |

**这一阶段缺两个路由，得加**：

1. **`/mutable/<file>`** —— ETag 每次请求都变（或按某个开关变）。
   用来验证 `If-Range` 不匹配 → 服务端回 200 → 你的程序丢弃 `.part` 从头下。
   **这是本阶段唯一没法用现有路由测的核心路径**，必须补。
2. **`/truncate/<file>`** 或者干脆手动改文件 —— 服务端上的文件**变短**，
   使得本地 `.part` 比服务端的 total 还大（第 5.1 节的第二档）。

## 11. 验收清单

| # | 场景 | 期望 |
| --- | --- | --- |
| 1 | `/ranged/test_100m.bin` 一次性下完 | 大小 == 100 MB，MD5 与源文件一致，产物是 `xxx.bin` 不是 `xxx.bin.part` |
| 2 | 限速到 ~2 MB/s，**中断 5 次以上**再续 | 最终 MD5 与 #1 一致 |
| 3 | 已下完后再跑一次 | 服务端回 416，程序识别为「已完成」，退出码 0，不重下 |
| 4 | 手动把 `.part` 截短 1 字节再跑 | 从正确位置续，MD5 一致 |
| 5 | `/mutable/...` 下一半后重跑 | 收到 200 → `.part` 截断到 0 → 重下 → MD5 是**新文件**的 |
| 6 | `/ignore/test_100m.bin` 下一半后重跑 | 识别为不可续传，从头下，且**不会**把新数据追加到旧的半截后面 |
| 7 | 本地 `.part` 比服务端 total 大 | 报错或丢弃重下，**绝不** rename 成品 |
| 8 | Ctrl+C | 优雅退出（`CURLE_ABORTED_BY_CALLBACK`），`.part` 保留，退出码可区分 |
| 9 | `/ranged/test_1g.bin` | >4 GB 边界虽然没到，但确认所有偏移量用的是 64 位类型；断点 >2 GB 时不溢出 |
| 10 | 目标文件已存在 | 按你定的策略执行（覆盖/加序号/报错），行为和 readme 写的一致 |

第 2 项的中断可以直接 Ctrl+C；要跑自动化就写个脚本，启动后 `sleep n` 再 kill。

校验和（Windows 自带，不用加依赖）：

```bash
certutil -hashfile test_100m.bin MD5
```
